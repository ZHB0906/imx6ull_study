# 一、本章要解决的矛盾

内核里有大量"看起来没问题、并发时一定出事"的代码。本章用一个能**量化**的实验把这件事讲透：

```
被保护的共享资源（两个）：
    unsigned long sw_count;   ——「开关被切换」的累计次数（典型"读-改-写"）
    int           cur_state;  ——当前逻辑状态

竞争窗口（为什么单核也会竞争）：
    进程 A 执行 sw_count 的"读 → 写回"时被时钟中断抢占，
    进程 B 进临界区读到同一个旧值 → A、B 都写回 old+1 → 丢一次更新。
    （单核上这个窗口只有 3 条指令，所以实验里用模块参数 windows_ms
      在【读】和【写回】之间插入一个窗口，把竞争稳定复现出来。）
```

# 二、一份源码、五种保护方式

`drivers/46_concurrency/beep_lock.c` 用编译期开关 `KIND` 出 5 个模块：

| KIND | 保护方式 | 关键 API | 能不能睡眠 | 中断上下文能用吗 |
|---|---|---|---|---|
| 0 | **无保护**（反面示范） | — | — | — |
| 1 | 原子操作 | `atomic_inc` / `atomic_read` | 不涉及 | 能 |
| 2 | 自旋锁 | `spin_lock_irqsave` / `spin_unlock_irqrestore` | **不能** | **能** |
| 3 | 信号量 | `down` / `up`（二值信号量当锁用） | 能 | 不能 |
| 4 | 互斥体 | `mutex_lock` / `mutex_unlock` | 能 | 不能 |

模块参数 `windows_ms`（默认 1）：

| 取值 | 用途 |
|---|---|
| `windows_ms=2` | 把临界区里的"读-改-写"窗口拉长 → **竞争复现** |
| `windows_ms=0` | 关闭窗口 → **基准测量**（看锁本身的开销） |

# 三、实测结果（2026-09-14，2 进程 × 200 次）

```
sh /mnt/nfs/root/46_race.sh 2 200
```

| KIND | 保护方式 | 竞争复现（期望 400） | 基准（2×5000 次写） |
|---|---|---|---|
| 0 | 无保护 | **202** ← 丢了 **198** 次（近一半） | 23 ms |
| 1 | 原子操作 | 400 ✅ | 24 ms |
| 2 | 自旋锁 | 400 ✅ | 27 ms |
| 3 | 信号量 | 400 ✅ | 29 ms |
| 4 | 互斥体 | 400 ✅ | 25 ms |

**读法**：

- 只有 KIND=0 丢更新，而且丢得极狠（两个进程几乎每次都读到同一个旧值）；
  其余四种**精确等于期望值** —— 这就是"保护"的意义。
- 基准那一列**差别很小**（23~29 ms / 10000 次 ≈ 每次 2.3~2.9 µs），而且顺序不完全
  符合"原子 < 自旋锁 < 信号量/互斥体"。原因很实在：**每次 write 都是一次系统调用**，
  时间主要花在 syscall 与调度的进出上，锁本身的开销被淹没了；单核板子上也没有
  真正的并行争抢。想看锁开销的差别，得让临界区在**内核里循环很多次**（见第六节）。
- 但**适用场合的差别是硬性的**：自旋锁临界区不能睡眠（本实验故意在 KIND=2 的临界区里
  放了 `mdelay` —— 那是反面教材），而信号量/互斥体可以睡眠，所以临界区里能
  `copy_from_user`、能等 I/O。选哪个不取决于"谁快"，而取决于**能不能睡眠**。

# 四、★ 本章踩坑 #13：实验脚手架自己先错了两次

第一次跑出来的是**五个体全都是 403、全都不丢**，看着像"锁都没用"，其实是测试写错了：

| # | 错在哪 | 后果 | 修法 |
|---|---|---|---|
| 1 | `mdelay` 放在 `sw_count++` **之前** | 真正需要拉长的"读→写回"之间只有 3 条指令，被抢占概率≈0 → 五种变体全都不丢，实验毫无区分度 | 窗口移到**读和写之间**：`tmp = sw_count; race_window(); sw_count = tmp + 1;` |
| 2 | `release()` 里也调了计数函数 | 每个子进程 `close()` 一次 + 测试程序开设备读一次，都会偷偷 +1 → 实际 403 而不是 400 | 拆出 `beep_set_gpio()`（只换电平、不计数），`release()` 走它 |
| 3 | 判据用无符号相减：`expect - got` | `400 - 403` 下溢成 **4294967293**，打印出"丢了 42 亿次"这种荒唐结论 | 分三种情况判断：`==` / `<` / `>` 各打一句人话 |

**教训**：做竞争实验，"窗口位置"和"账目干净"比锁本身更容易出错；
先让**无保护**那一版稳定丢更新，才说明实验有效（这就是阳性对照）。

# 六、下一步（可选）

1. **更硬的基准**：给驱动加一个 `ioctl(fd, CMD_LOOP, N)`，让内核在一次系统调用里
   循环 N 次临界区 —— 这样锁的开销才能从 syscall 噪声里分离出来，横向对比才公平。
2. **多进程压力**：`sh /mnt/nfs/root/46_race.sh 4 300`（或 `8 200`）看丢更新比例的变化。
3. **中断上下文版本**：把自旋锁换成 `spin_lock`（不关中断）再对比，能讲清
   `spin_lock_irqsave` 为什么要关中断。
